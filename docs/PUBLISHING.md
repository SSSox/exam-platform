# Публикация на GitHub Pages

Приложение и банки публикуются отдельно, каждое из своего репозитория:

- Репозиторий банков превращается в статический сайт с `index.json`, `nodes/` и `banks/`.
- Приложение собирается без встроенного контента и при запуске скачивает банки с адреса этого сайта.

Адреса репозиториев в документе условные. Ниже `<пользователь>` это ваш аккаунт или организация на GitHub, `<репозиторий-банков>` и `<репозиторий-кода>` имена ваших репозиториев. Адрес банков самого проекта записан в `content-sources.json` в корне репозитория кода; публикуя свою копию, замените его на свой.

## Что нужно заранее

- Два репозитория на GitHub: с кодом (`exam-platform`) и с банками (`exam-content`). Шаблон для банков ниже берёт командную строку из репозитория кода; для закрытого репозитория кода понадобится токен доступа.
- В настройках каждого репозитория: Settings, Pages, Source: GitHub Actions.
- Страница приложения грузит контент только с `https://*.github.io` и `https://cdn.jsdelivr.net` (политика CSP в `apps/ui/index.html`). Для сайта на своём домене добавьте его в `connect-src` в этом файле и пересоберите приложение.
- Хостинг банков должен разрешать чтение файлов с другого источника (CORS), ведь приложение размещено на другом адресе. После первой публикации откройте приложение и загляните в консоль браузера: ошибка CORS означает, что хостинг этого не разрешает.

## Проверка перед публикацией

Из корня репозитория кода, на папке с банками (путь свой):

```bash
node packages/content-tools/src/cli.ts validate <папка-банков>
node packages/content-tools/src/cli.ts compile <папка-банков> <куда-собрать>
```

`validate` печатает число банков и вопросов или список ошибок. `compile` сам проверяет контент и при ошибках ничего не пишет. Папку назначения `compile` стирает перед сборкой, поэтому она не должна лежать внутри папки банков, содержать её или совпадать с ней. Стирает она только пустую папку или прежнюю сборку (внутри лишь `nodes`, `banks`, `index.json`); с любой другой папкой команда остановится, ничего не удалив.

## Публикация банков

Репозиторий банков публикуется целиком: workflow проверяет контент, собирает его командой `compile` и выкладывает результат на Pages. Корнем сайта становится папка со сборкой, поэтому адрес для приложения такой:

```
https://<пользователь>.github.io/<репозиторий-банков>
```

Шаблон `.github/workflows/pages.yml` для репозитория банков.

> Шаблон не запускался. Адреса репозиториев подставьте свои, версии действий сверьте с актуальными.

```yaml
name: Publish content

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  publish:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      # Банки лежат в корне этого репозитория; кладём их в подпапку content.
      - uses: actions/checkout@v4
        with:
          path: content

      # Код нужен только ради командной строки. Подставьте свой репозиторий кода.
      - uses: actions/checkout@v4
        with:
          repository: <пользователь>/<репозиторий-кода>
          ref: main
          path: code

      - uses: actions/setup-node@v4
        with:
          node-version: 26

      - name: Install the command line
        working-directory: code
        run: npm ci

      - name: Validate
        run: node code/packages/content-tools/src/cli.ts validate content

      # Папка site лежит рядом с content, а не внутри: compile стирает папку назначения.
      - name: Compile
        run: node code/packages/content-tools/src/cli.ts compile content site

      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site
      - id: deployment
        uses: actions/deploy-pages@v4
```

После первого запуска откройте `https://<пользователь>.github.io/<репозиторий-банков>/index.json`: в ответе должен быть JSON с полями `version`, `kinds` и `roots`.

## Публикация приложения

Приложение собирается без встроенного контента (`EXAM_CONTENT_DIR=none`) и с адресом сайта банков. Адрес лежит в `content-sources.json` в корне репозитория кода (поле `urls`), переменная `VITE_CONTENT_URLS` заменяет его на время одной сборки. Оба читаются при сборке и вшиваются в код, поэтому смена адреса требует новой сборки. Результат лежит в `apps/ui/dist`, пути в нём относительные, так что сайт работает и в подпапке `/<репозиторий-кода>/`. Адреса страниц построены на `#`, настраивать перенаправления не нужно.

Локально, из корня репозитория кода:

```bash
EXAM_CONTENT_DIR=none VITE_CONTENT_URLS=https://<пользователь>.github.io/<репозиторий-банков> npm --prefix apps/ui run build
```

В PowerShell:

```powershell
$env:EXAM_CONTENT_DIR = "none"
$env:VITE_CONTENT_URLS = "https://<пользователь>.github.io/<репозиторий-банков>"
npm --prefix apps/ui run build
```

В этом репозитории это делает [`.github/workflows/pages.yml`](../.github/workflows/pages.yml). При каждом push в `main` он проверяет типы и тесты, собирает страницу с `EXAM_CONTENT_DIR=none` и публикует её; правки только в документации сборку не запускают. Адрес банков workflow берёт из `content-sources.json`, поэтому в форке достаточно поменять этот файл. В настройках репозитория (Settings, Pages) источником должен стоять «GitHub Actions».

Приложение будет доступно по адресу `https://<пользователь>.github.io/<репозиторий-кода>/`.

## Как обновляются данные

- Правка банка: коммит в репозиторий банков, workflow собирает сайт заново. Приложение при запуске перечитывает `index.json` без кэша, видит новую версию и скачивает только те файлы, у которых изменился хэш. Пересобирать приложение не нужно.
- Смена адреса сайта с банками или появление второго зеркала: правка `content-sources.json` (или `VITE_CONTENT_URLS` для одной сборки) и новая сборка приложения.
- Адреса банков не отвечают: приложение показывает последний сохранённый каталог с пометкой «Нет сети, показаны сохранённые данные», а банки и узлы, которые уже открывали, читает из кэша. Если на устройстве ничего не сохранено, оно берёт `index.json` из встроенного снимка, с той же пометкой. В сборке без снимка (`EXAM_CONTENT_DIR=none`) первый запуск без сети покажет ошибку загрузки.

## Установщик для Windows

Настольная версия собирается командой `npx tauri build` из `apps/desktop` и запускает ту же сборку интерфейса. Если нужен установщик со встроенными банками, соберите его без `EXAM_CONTENT_DIR=none`: контент возьмётся из соседней папки `exam-content` или из переменной `EXAM_CONTENT_DIR`. С `VITE_CONTENT_URLS` установщик сможет обновлять банки по сети.

## Ссылки на Windows и Android в веб-версии

Веб-версия показывает ссылки на установщики в строке под списком предметов и в карточке «Приложение» в настройках. В приложениях для Windows и Android этих ссылок нет. На телефоне с Android первой стоит ссылка на Android.

Адреса лежат в `downloads.json` в корне репозитория кода (поля `windows` и `android`) и вшиваются при сборке, как адрес банков. Переменные `VITE_DOWNLOAD_WINDOWS` и `VITE_DOWNLOAD_ANDROID` заменяют их на одну сборку. Значение `none` убирает ссылку (в `downloads.json` можно оставить и пустую строку), без обеих ссылок блок не показывается. Адрес, который не начинается с `https://`, останавливает сборку. В `downloads.json` проекта записан его собственный репозиторий; публикуя свою копию, замените адреса, поставьте `none` или удалите файл.

Адреса по умолчанию ведут на файлы последнего релиза репозитория кода:

```
https://github.com/<пользователь>/<репозиторий-кода>/releases/latest/download/exam-trainer-windows-setup.exe
https://github.com/<пользователь>/<репозиторий-кода>/releases/latest/download/exam-trainer-android.apk
```

Пока такого релиза нет, ссылки отвечают 404. Выпуск релиза описан в разделе «Выпуск релиза».

## Автообновление приложений

Приложения для Windows и Android раз в день, через несколько секунд после запуска или при возврате в приложение, читают `latest.json` из последнего релиза репозитория кода:

```
https://github.com/<пользователь>/<репозиторий-кода>/releases/latest/download/latest.json
```

Адрес берётся из `plugins.updater.endpoints` в `apps/desktop/src-tauri/tauri.conf.json` и вшивается при сборке, в APK тоже. Если в `latest.json` версия выше установленной, в настройках и под списком предметов появляется кнопка «Обновить» с размером файла. Скачивание начинается только по нажатию. В настройках есть и кнопка «Проверить обновления». Веб-версии автообновление не нужно: каждый заход открывает свежую сборку сайта.

Перед установкой приложение проверяет скачанный файл:

- Windows проверяет подпись установщика открытым ключом из `plugins.updater.pubkey`, а подписанная версия должна совпасть с версией в `latest.json`. Затем установщик работает без вопросов (окно с ходом установки), приложение закрывается и запускается новой версией.
- Android сверяет размер и SHA-256 с `latest.json`, затем имя пакета, версию APK (она должна совпасть с версией в `latest.json`), номер сборки (он должен быть выше установленного) и сертификат подписи APK: он должен совпасть с сертификатом установленного приложения. После этого Android показывает свой диалог установки. В первый раз он попросит разрешить приложению устанавливать файлы.

Файлы в `latest.json` должны лежать в релизе `v<версия>` того же репозитория, другие адреса приложения не скачивают. Файл, не прошедший проверку, удаляется, а приложение предлагает скачать новую версию вручную. Прогресс и настройки при обновлении сохраняются.

Windows без открытого ключа (пустой `pubkey`) обновлений не ищет и карточку не показывает. Android ключ обновлений не использует: подлинность APK он проверяет по сертификату подписи. Поэтому хранить нужно оба ключа: ключом обновлений подписывается установщик для Windows, ключом APK каждая новая версия для Android. Версии, вышедшие до появления автообновления, и установщики Windows, собранные без ключа, сами не обновятся: новую версию в них нужно один раз поставить вручную.

### Ключ обновлений

Создаётся один раз, из `apps/desktop`:

```bash
npx tauri signer generate -w ~/.tauri/exam-trainer.key
```

Команда спросит пароль и запишет два файла: закрытый ключ `exam-trainer.key` и открытый `exam-trainer.key.pub`. Строку из `.pub` вставьте в `plugins.updater.pubkey` в `tauri.conf.json` и закоммитьте. Закрытый ключ держите вне репозитория (git не видит файлы `*.key`) и сохраните его копию вместе с паролем. Если его потерять, приложения с прежним открытым ключом новые версии не примут.

## Подпись установщика Windows (SignPath)

Установщик без подписи кода Windows SmartScreen встречает предупреждением «Неизвестный издатель». Открытые проекты могут подписываться бесплатно через [SignPath Foundation](https://signpath.org), но подписывают там только то, что собрал GitHub Actions из репозитория проекта. Поэтому установщик для релиза собирает workflow [`.github/workflows/release.yml`](../.github/workflows/release.yml). Ключ APK и ключ обновлений в GitHub не попадают: APK и `latest.json` по-прежнему готовятся на вашем компьютере.

Workflow запускается тегом `vX.Y.Z` или вручную (Actions, Windows installer, Run workflow). Он берёт банки из репозитория `exam-content` того же владельца (репозиторий должен быть публичным), проверяет код и банки, собирает приложение и отправляет `exam-desktop.exe` на подпись. Затем упаковывает подписанное приложение в установщик и отправляет на подпись установщик. Каждую из двух подписей вы подтверждаете в SignPath, workflow ждёт подтверждения до двух часов. Готовый установщик лежит 14 дней в артефакте `windows-installer-<версия>` на странице запуска. Пока SignPath не настроен, workflow собирает, проверяет и пробно устанавливает то же самое, только без подписи. Запуск останавливается, если в этом коммите пустой `plugins.updater.pubkey`: такой установщик никогда не обновится сам.

Настройка, один раз:

1. Подайте заявку на [signpath.org](https://signpath.org). Их условия: открытая лицензия (GPL подходит), никакого закрытого кода, двухфакторный вход на GitHub и в SignPath у всех участников, а проект уже выпущен в том виде, в каком будет подписываться. Поэтому первый релиз выходит без подписи. Раздел «Политика подписи кода», который требует SignPath, в README уже есть.
2. Пройдите настройку, которую предложит SignPath после одобрения (организация, проект, политика подписи, подключение GitHub Actions как источника сборки). Репозиторий ждёт в проекте две конфигурации артефактов со слагами `application` и `installer`: создайте их и вставьте в них файлы из [`.signpath/artifact-configurations/`](../.signpath/artifact-configurations/).
3. В репозитории на GitHub (Settings, Secrets and variables, Actions) задайте переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT` (слаг проекта) и `SIGNPATH_POLICY` (`release-signing`; для пробы с тестовым сертификатом `test-signing`) и секрет `SIGNPATH_API_TOKEN`.
4. Допишите в раздел «Политика подписи кода» всех трёх README строку, которую требует SignPath: «Free code signing provided by [SignPath.io](https://about.signpath.io), certificate by [SignPath Foundation](https://signpath.org)».

С политикой `release-signing` workflow принимает файлы только с действительной подписью SignPath Foundation (с `test-signing` любую подпись: тестовому сертификату Windows не доверяет), а после подписи ставит установщик в пустую папку и проверяет подпись установленного приложения. Программа удаления, которую NSIS кладёт рядом с приложением, отдельной подписи не получает.

## Выпуск релиза

1. Поднимите `version` в `apps/desktop/src-tauri/tauri.conf.json` (только вида `0.2.0`). Из неё берутся номер в имени установщика и версия APK.
2. Соберите подписанный APK (`npx tauri android build --apk --target aarch64`, подпись описана в README). Установщик возьмите из GitHub Actions: отправьте тег (`git tag v0.2.0`, `git push origin v0.2.0`) или запустите workflow вручную, подтвердите обе подписи в SignPath и скачайте артефакт `windows-installer-0.2.0`. Это zip-архив, в нём `exam-trainer-windows-setup.exe`. Без SignPath установщик можно собрать и у себя: `npx tauri build` в `apps/desktop`. Скрипт из следующего шага откажется работать, если APK или установщик старой версии.
3. Задайте закрытый ключ обновлений и запустите `npm run release` из корня репозитория. `--windows` указывает на установщик из GitHub Actions; без этого параметра скрипт берёт установщик локальной сборки:

   ```bash
   export TAURI_SIGNING_PRIVATE_KEY_PATH="$HOME/.tauri/exam-trainer.key"
   export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="<пароль>"
   npm run release -- --windows="$HOME/Downloads/exam-trainer-windows-setup.exe"
   ```

   В PowerShell переменные задаются так: `$env:TAURI_SIGNING_PRIVATE_KEY_PATH = "$HOME\.tauri\exam-trainer.key"`.

   Скрипт кладёт в `release/` (git её не видит) установщик и APK под именами `exam-trainer-windows-setup.exe` и `exam-trainer-android.apk`, подписывает оба ключом обновлений и записывает `latest.json`. Эта подпись ставится на уже подписанный SignPath файл, поэтому сначала SignPath, потом `npm run release`. Скрипт не примет установщик другой версии, само приложение вместо установщика и установщик без действительной подписи кода. Пока SignPath не одобрил проект, добавьте `--unsigned`: тогда установщик без подписи пройдёт с предупреждением. `--notes="..."` добавляет описание в `latest.json`.
4. Опубликуйте релиз командой, которую напечатал скрипт, или вручную на GitHub (Releases, Draft a new release) с теми же тремя файлами:

   ```bash
   gh release create v0.2.0 release/exam-trainer-windows-setup.exe release/exam-trainer-android.apk release/latest.json --title v0.2.0 --notes "Code signing policy: https://github.com/<пользователь>/<репозиторий-кода>/blob/main/README.en.md#code-signing-policy"
   ```

   Ссылку на политику подписи кода SignPath требует на каждой странице релиза.

Тег должен быть ровно `v` и версия из `tauri.conf.json`: `latest.json` ссылается на файлы этого тега. `latest` указывает на последний опубликованный релиз, черновики и пре-релизы он пропускает, так что приложения увидят новую версию только после публикации. В релизе всегда оба файла: по `latest` веб-версия ведёт и на установщик, и на APK. Веб-версию пересобирать не нужно.
